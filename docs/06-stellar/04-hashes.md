# Canonicalización, hashes y verificador

**Estado:** P0 normativo · **Versión:** 1.0 · **Fecha:** 2026-11-26

Algoritmo SHA-256, salida lowercase 64 hex en API/DB; chain BytesN<32>. `questionIdChain=SHA256(UTF8(uuid lowercase))`. Para documentos JSON: usar perfil `praev-c14n-v1`, objetos keys ASCII ordenadas lexicográficamente, arrays mantienen orden, sin whitespace, UTF-8, strings NFC, números enteros seguros (no -0, NaN, float, bigint directo), boolean/null; rechazar keys no ASCII o valores inválidos, normalizar strings antes de serializar con `JSON.stringify` y validar entradas. No confiar en orden de JSONB. Guardar bytes canónicos exactos como bytea, no reserializar para verificar. No afirmar compatibilidad RFC 8785 completa. `specHash=SHA256(canonicalBytes(spec))`; `rationaleHash` del payload con schema, questionId, forecaster, seq, probabilityBps, informationCutoff, evidenceIds ordenados según payload y rationale; `evidenceHash` del manifest de resolución con hashes de archivos. Raw bytes se hashean directamente. Dominios separados mediante campo schema constante.

Verificador: descargar payload, recalcular hash, comparar con chain; verificar id derivado, contractId/red, tx o estado y campos relevantes. El contrato no recalcula JSON: operador/cliente debe comprobar que campos de spec (fechas, roles, mode) coinciden con argumentos chain; mismatch no verifica. Una tx exitosa para otro contrato no es prueba. Mostrar tres resultados: `match`, `mismatch`, `unavailable`. El hash prueba integridad, no autoría de la fuente ni verdad.

Vectores mínimos: SHA256 ASCII `abc` = `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`. `{"b":2,"a":1}` y `{"a":1,"b":2}` canonicalizan a `{"a":1,"b":2}`. Cambiar un byte, un campo o el orden de array cambia hash. Probar NFC y rechazo de floats. JS browser usa Web Crypto, Node crypto; mismo canonicalizer compartido.
